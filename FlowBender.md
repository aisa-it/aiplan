# FlowBender — ИС ИНТЦ «Сириус» поверх ядра АИПлан

Придаток к `CLAUDE.md`. Описывает, что нужно сделать в **этом** репозитории (ядро), чтобы на нём собралась
заказная система, и как понятия ТЗ ложатся на сущности АИПлан. Читать после `CLAUDE.md`, разделы
«Ядро и подключаемые движки» и «Интерфейс движка» — здесь они не повторяются.

**Источник:** задача `sirius-INTDEV-1`, вложение «ТЗ_разработка_ИС_Сириус_Резиденты_v9_по_образцу.docx»
(предварительная версия, на согласовании с разработкой). Замечания к ТЗ пишутся в комментарии к задаче,
не в код. Сроки: этап 1 — до 10.12.2026 (ПМИ до 25.12.2026), этап 2 — до 16.03.2027 (ПМИ до 30.03.2027).

## Что это и где живёт

- **FlowBender** — приватный Go-модуль: `engine.Engine` + свои модели, роуты, cron, MCP-инструменты, шаблоны
  документов, интеграция с ГИС ЕЦП. Зависит от `aiplan` как от библиотеки, свой `cmd/main.go`, Dockerfile, helm.
- **Фронт** — приватный каталог, подключаемый через alias `@ext` (страницы реестров, карточек заявок, документов,
  дашбордов, навигация, переименование сущностей).
- **Этот репозиторий** — только ядро: точки расширения, которых движку не хватает, и **ничего заказного**.
  Никаких «ИНТЦ», «резидент», «эксперт», «ГИС ЕЦП» в коде и комментариях ядра. Расширение должно быть
  общим: «хук на вложение», а не «лимит 25 МБ для заявки».

Правило разделения: если фича нужна любому заказному движку — в ядро; если она про предметную область
Сириуса — в FlowBender. Сомнение решается в пользу FlowBender.

## Роли ТЗ и как они ложатся на АИПлан

ТЗ задаёт шесть ролей с иерархическим включением: Оператор ⊂ Главный оператор ⊂ Руководитель; отдельно
Ответственный секретарь, Эксперт, Администратор. Права заданы матрицей «функция × роль» в разрезе типа
заявки и стадии (таблицы 4.1–4.8 ТЗ).

| ТЗ | АИПлан |
|---|---|
| Роль ТЗ | Собственная таблица FlowBender «пользователь → роль» на уровне пространства. Роли ядра (5/10/15) — подложка: все сотрудники Member, Администратор — Admin пространства |
| Матрица прав | `engine.Authorizer` в FlowBender: `Action` + роль + статус задачи (Target) → `Verdict`. Ядро не трогать |
| Право на переход статуса | `engine.StatePolicy` в FlowBender поверх `states_flow` проекта: `CanTransition` смотрит роль, `ScopeAvailableStates` согласован с ней |
| Изоляция эксперта | `engine.VisibilityPolicy` в FlowBender: для роли Эксперт видны только задачи, где он исполнитель. Требует доработки ядра (см. ниже) |
| Администратор | Admin пространства ядра + функции админки FlowBender (роли, справочники, журналы, дашборды) |
| Директор ИНТЦ | Не пользователь. В Системе только сканы его подписи |

## Карта понятий ТЗ → сущности АИПлан

Одно пространство (workspace) на инсталляцию. Тип заявки = проект: у каждого проекта свой набор статусов и
свой граф переходов, идентификатор проекта даёт суффикс типа в номере.

| Понятие ТЗ | Сущность АИПлан | Примечание |
|---|---|---|
| Заявка (8 типов, 4.2.1) | `Issue` в проекте своего типа | Проекты: краткое описание, формальная проверка, экспертиза, статус резидента, отчёт, услуга, исключение, выписка |
| Регистрационный сквозной номер | Таблица FlowBender «обращение» + `issue_id` каждого этапа | `sequence_id` ядра остаётся внутренним; цепочка «краткое описание → экспертиза → свидетельство» связана через обращение. Ядро не менять |
| Статусная модель типа (таблицы 4.12–4.31) | `dao.State` + `states_flow` проекта | Статусы и переходы FlowBender сеет при старте; завершающие статусы — группы `completed`/`cancelled` |
| Задание эксперта (4.15) | `Issue` в проекте «Задания экспертов», `parent` — заявка на экспертизу, исполнитель — эксперт | Изоляция — через видимость, не через отдельный механизм |
| Исполнитель заявки | `Assignees` (один) | Автоназначение «тот же, что на предыдущем этапе» — `IssueHooks`/логика FlowBender при создании |
| Срок исполнения | `TargetDate` | Расчёт в рабочих днях, календарь праздников и справочник нормативных сроков — в FlowBender |
| Приостановка срока на уточнении | Поле FlowBender на задаче/обращении | Ядро не знает о паузах |
| Данные заявки (таблицы 4.10, 4.11, 4.16, прил. 8) | JSONB-полезная нагрузка из ГИС ЕЦП в таблице FlowBender + ключевые поля дублируются в `IssueProperty` для фильтров | Типы полей ядра (`string/boolean/select/multiselect/link/lookup/date/datetime`) не покрывают файлы, числа и таблицы-дорожные карты. Не расширять ядро под это |
| Внутренние комментарии | `IssueComment` ядра | |
| Внешние комментарии (для заявителя) | Модель FlowBender «сообщение заявителю», уходит в ГИС ЕЦП | В ядре нет признака видимости комментария; не добавлять — внешние сообщения всё равно живут в интеграции |
| Вложения заявки | `FileAsset` + MinIO (tus-загрузка) | Лимит ядра захардкожен (4 ГБ), проверки MIME нет, версий файлов нет. Форматы и лимиты 25/100 МБ — проверка в FlowBender через хук ядра (см. ниже) |
| История обработки | `activity-tracker` ядра (`ActivityEvent`, слои issue/project/doc/form/sprint/workspace) | Слои фиксированы; для собственных моделей FlowBender ведёт историю сам |
| Реестры: ЮЛ, ФЛ, экспертов, исполнителей услуг (4.2.3) | Модели FlowBender + роуты через `RegisterRoutes` | Не задачи и не справочники ядра: нужны карточки, история, связи с заявками |
| Каталог услуг (4.2.5) | Модель FlowBender | Документы к услуге — через `file-storage` ядра |
| Справочники Администратора (направления, секции, нац. цели, сроки) | `Dictionary`/`DictionaryRow` ядра (архивация есть) либо таблицы FlowBender | Справочник сроков — FlowBender, остальные — по месту |
| Регулярные отчёты (4.2.4, этап 1) | `Issue` в проекте «Отчётность» + JSONB прил. 8 | Перечень «не сдавших» и напоминания за 30 дней — cron FlowBender |
| Разовые отчёты, конструктор (этап 2) | Модуль форм ядра как конструктор (`Form.Fields`) → схема формы уходит в ГИС ЕЦП; ответ приходит через интеграцию → `FormAnswer` → задача | Публичная страница ответа ядра не используется: резиденты в Системе не работают |
| Документы (4.2.7) | Реестр документов FlowBender: метаданные, версии файлов, `.sig`, факт простой ЭП | Файлы — `file-storage` ядра. `pkg/export` ядра — PDF задачи через `fpdf` с захардкоженной вёрсткой, DOCX нет; генерация документов по шаблонам целиком в FlowBender |
| Уведомления (таблица 4.40) | Уведомления ядра: приложение (websocket), e-mail, Telegram; отложенные (`DeferredNotifications`, в т.ч. `deadline_notification` по `TargetDate`) | Рождаются только из `ActivityEvent` по сущностям ядра — движку нужен вход (см. ниже). Шаблоны писем переопределяются через `dao.Template` из БД |
| Рассылки | Модель FlowBender + отправка почты средствами ядра | В ядре рассылок нет и не будет |
| Журнал действий Администратора | activity ядра + журнал FlowBender для своих моделей | |
| Технический журнал, мониторинг | Логи приложения + метрики `:2112` | |
| Аутентификация «Сириус Паспорт» | `auth-provider` ядра | В ядре только LDAP по логину/паролю (`AuthProvider.AuthUser(email, password)`), редиректного OIDC/OAuth2-флоу нет — нужно в ядро (см. ниже). Протокол уточнить у заказчика |
| ГИС ЕЦП | Роуты FlowBender в группе без авторизации ядра, своя аутентификация интеграции | Контракт целиком на этапе 1, спецификация от заказчика |
| Аналитика, дашборды, сводные отчёты (этап 2) | Модели FlowBender, cron-агрегация раз в час, выгрузка xlsx | Ядро не участвует |
| Учётные записи | `User` ядра (`is_active`, `blocked_until`) | Роль — FlowBender |

## Что сделать в ядре (этот репозиторий)

Только то, без чего FlowBender не соберётся или соберётся с обходами. Каждый пункт — общий механизм.

### Этап 1 (нужно к декабрю 2026)

1. **`CanViewIssue` на HTTP.** Сейчас построчная проверка видимости подключена только к MCP `get_issue`.
   Для изоляции экспертов её надо вызвать в `getIssue` и во всех ручках issue-скоупа, отдающих данные задачи
   (комментарии, вложения, история, связи). Место — guard после `FindIssueByIdOrSeqMiddleware` или в
   `permissionMiddleware` для просмотровых действий. Обновить golden-эталоны `authz_matrix`.
2. **Хук на вложения.** В `engine.IssueHooks` добавить `BeforeAttachmentAdd(ctx, s Subject, issue dao.Issue, meta AttachmentMeta) (Verdict, error)`
   с именем, размером и типом файла. Вызывать из tus-хука (там `apicontext` нет — субъект через
   `LoadIssueSubject`). Дефолтный движок отдаёт `Default`.
3. **Уведомления из движка.** Сейчас уведомления рождаются только из `dao.ActivityEvent` по слоям ядра
   (`EventHandler` выбирается по `EntityLayer`), а отложенные — по фиксированному набору типов в
   `notification_processor.go`. Дать движку вход: `Core.Notifications()` с методом
   `Notify(ctx, userID, Notification)` (приложение + почта + Telegram по настройкам пользователя, свой шаблон
   письма через `dao.Template`) и возможность регистрировать свой тип отложенного уведомления с обработчиком.
4. **Хук после миграции.** `Engine.Init` вызывается **до** `AutoMigrate`, поэтому сеять статусы, проекты и
   справочники в `Init` нельзя. Добавить `Core.RegisterPostMigration(fn func(ctx, *gorm.DB) error)`.
5. **Политика и поиск для роутов движка.** `Core` не отдаёт `*policy.Policy` и `*search.Searcher`; свои ручки
   FlowBender обязаны проверять права тем же механизмом. Добавить `Core.Policy()` и `Core.Search()`.
   Проверить, что `pkg/engine` при этом не потянет запрещённые зависимости (`go list -deps ./pkg/engine`);
   если тянет — отдать через интерфейсы в `pkg/engine`.
6. **Хук на комментарий.** `BeforeCommentCreate/Update/Delete` в `IssueHooks` — чтобы FlowBender мог
   запретить эксперту комментировать чужое и закрыть комментарии в завершающих статусах.
7. **Аутентификация OIDC.** `auth-provider` знает только `AuthUser(email, password)` и LDAP; редиректного
   флоу в ядре нет. Добавить общий OIDC-провайдер: authorization code, callback-роут, userinfo/claims,
   настраиваемые endpoints и маппинг claim → `User` (e-mail, ФИО, внешний идентификатор), автосоздание
   пользователя как в LDAP. Конфиг — переменные `OIDC_*`. Под «Сириус Паспорт» ничего специального не писать:
   если протокол окажется не OIDC, адаптер живёт в FlowBender поверх того же интерфейса.
8. **Внешний идентификатор пользователя.** Для маппинга учёток из внешнего провайдера нужно поле у `User`
   (`external_id` + провайдер), если его нет после п. 7 — завести там же.
9. **Манифест движка для фронта.** В ответ `GET /api/version/` (`pkg/server/routes.go`, сейчас
   `{version, sign_up, demo, ny, captcha, jitsi}`) добавить `engine: {name, entities: {...},
   hidden_modules: [...], nav: [...]}`, заполняемый движком через `Core.SetManifest(...)`. Дефолтный движок —
   пустой манифест.
10. **Фронт: alias `@ext`.** `aiplan-front/src/ext/index.ts` в репе нет, хотя `CLAUDE.md` его описывает.
    Завести стаб (пустые `routes`, `layout`, `nav`, i18n-оверрайды) и env-переменную сборки, перенаправляющую
    alias на каталог приватной репы. Переименование сущностей требует i18n во фронте — оценить отдельно.

### Этап 2 (к марту 2027)

11. **Формы как конструктор.** Конструктор и типы полей уже есть (`numeric, checkbox, input, textarea,
    color, date, attachment, select, multiselect`, `Validate`, `DependOn`, `PropertyTemplateId`). Не хватает:
    ручки, отдающей схему формы без публичной страницы, и приёма `FormAnswer` через API от имени интеграции
    (не no-auth браузерный сценарий, лимит вложения 50 МБ там свой). Проверить `FormAnswer → Issue` с
    `PropertyTemplateId` и отсутствие побочного создания задачи там, где нужна только карточка отчёта.

### Не делать в ядре

- Числовые/файловые/табличные типы `ProjectPropertyTemplate` под данные заявок — нагрузка живёт в FlowBender.
- Генерация документов и DOCX в `pkg/export`: там PDF задачи с захардкоженной вёрсткой, шаблонов нет.
  Шаблоны и рендер — в FlowBender.
- Общий слой трекера для чужих моделей — FlowBender ведёт историю своих таблиц сам.
- Версионирование `FileAsset` — версии документов хранит реестр документов FlowBender, ссылаясь на разные
  ассеты.
- Признак «внешний/внутренний» у комментариев ядра.
- Сквозная нумерация поверх `sequence_id`.
- Рабочие дни, праздники, SLA, паузы срока.
- Роли сверх 5/10/15.
- Рассылки, дашборды, реестры, документы с подписью.

## Что живёт в FlowBender (для ориентира, здесь не реализуется)

- `engine.Engine` + `Authorizer` + `StatePolicy` + `VisibilityPolicy` + `IssueHooks`.
- Модели: роли пользователей, обращения и номера, полезная нагрузка заявок, задания экспертов (связки),
  реестры (ЮЛ, ФЛ, эксперты, исполнители), каталог услуг, отчётные периоды и карточки отчётов, разовые отчёты,
  документы и версии файлов, подписи (`.sig` CAdES: разбор атрибутов сертификата без сертифицированной
  криптографии), рассылки, справочник сроков, календарь рабочих дней, дашборды и агрегаты.
- Cron: контроль сроков и напоминания, «не сдавшие отчёт», урегулирование, срок действия экспертизы
  (6 месяцев), агрегация аналитики раз в час.
- Роуты: интеграция ГИС ЕЦП (приём заявок, отзывов, доработок, ответов; передача статусов, документов,
  событий), реестры, документы, рассылки, админка, аналитика. Все — через `policy.Authorize`.
- MCP-инструменты по заявкам и реестрам — через `RegisterMCPTools`, права те же.
- Сид при старте: пространство, проекты по типам заявок, статусы и графы переходов, справочники.

## Спорные места ТЗ (для комментариев к задаче, не для кода)

- **«Задания экспертов» и таблица 4.15**: задание переходит по статусам параллельно заявке (4.14). Два графа на
  одну сущность в АИПлан не бывает — задание должно быть отдельной задачей. Согласовать формулировку.
- **Формы 4.10/4.11**: 23 раздела с файлами и таблицей дорожной карты — это данные ГИС ЕЦП, Система их только
  показывает. Настаивать, что редактирование в Системе не требуется.
- **Уточнение эксперта «не меняет статус заявки», но меняет статус задания** — согласуется с моделью «задание =
  отдельная задача».
- **Простая ЭП Руководителя** в интерфейсе — это подтверждающее действие с записью в журнал; убедиться, что
  заказчик не ждёт криптографии.
- **УКЭП без сертифицированных СКЗИ**: только разбор CAdES и проверка математики подписи; проверка по
  доверенным ЦС и штампам времени — вне объёма. Зафиксировать в ТЗ.
- **Сириус Паспорт**: протокол не назван. Запросить спецификацию до старта этапа 1.
- **Аналитика «раз в час» и 95-й процентиль 5 секунд** — совместимы только при предрасчёте; так и делать.
- **Горизонтальное масштабирование** отложено ТЗ на «дальнейшее развитие» — websocket-уведомления ядра
  живут в процессе; при одном инстансе проблем нет.

## Правила работы по FlowBender в этом репозитории

- Расширение ядра оформлять как общую точку расширения с дефолтным поведением `Default`/no-op; контракт
  закреплять `var _ engine.X = (*Y)(nil)`.
- Любое новое действие — в `engine.Action` + правило в `authz-areas.go`/`authz-target.go` или в
  `UncheckedActions`; golden-эталоны обновлять и смотреть diff.
- Новый хук — в `IssueHooks` с реализацией в `defaultengine/hooks.go` и обёрткой в `pkg/policy`.
- Новое поле `Core` — реализовать в `coreAdapter` (`pkg/server/engine.go`), регистрация только до конца `Init`.
- Проверять `go list -deps ./pkg/engine`: пакет не должен зависеть от `search`, `cache`, `api-context`,
  `server`, `mcp`, `notifications`.
- Комментарии в коде — общие, без ссылок на заказчика и эту задачу.
